# 象形英语小程序 MVP 产品文档（修订版）

## 1. 文档目的

这份文档的目标，是把当前的界面原型和业务想法，收束成一个真正可以开发、试用、收集反馈的最小可行版本。

这份修订版重点解决五件事：

1. 明确第一版到底先做什么。
2. 明确哪些“看起来像可选项”的能力，其实是上线必备的基础设施。
3. 把用户端、内容端、管理端、服务端的边界理清。
4. 避免把 MVP 做成“大而全但无法维护”的产品。
5. 给后续 vibe coding 留下一条更稳的执行路径。

---

## 2. 一句话产品定义

`象形英语小程序` 第一版，不是完整的英语学习平台，而是一个把《象形英语》的“老师讲解能力”搬到手机里的查词讲解服务。

用户输入一个单词后，应该能马上得到：

- 这个词是什么意思
- 这个词怎么拆
- 这个词对应的词根/词缀是什么意思
- 这个词在讲解视频中的对应片段
- 这个词在书中的页码或索引位置

---

## 3. 当前产品要解决的核心问题

### 3.1 用户问题

根据你 Word 文档里的记录，用户真实痛点很明确：

1. 书是静态的，但“象形拆解”需要动态讲解。
2. 很多家长买书给孩子后，孩子自己看不懂，也没有老师在旁边讲。
3. 直播讲解效果明显好于看书，说明用户真正需要的是“带解释的服务”，不是一本电子书。
4. 纸质书不方便随时查、不方便携带、不方便快速定位到某个词。
5. 用户已经开始问“有没有电子版”，说明数字化入口已经有现实需求。

### 3.2 业务问题

从业务角度，这个产品也在解决三个问题：

1. 纸质书传播链路长，作者和读者之间缺少持续连接。
2. 纸质内容容易被盗版，但持续更新的讲解服务更难被复制。
3. 只卖书是一次性收入，而查词服务、课程、会员是持续收入。

### 3.3 结论

所以第一版不是在做“电子书”，也不是在做“大而全的背单词 App”，而是在做：

`一本书的数字化讲解入口 + 一个可持续提供服务的轻量产品。`

---

## 4. MVP 结论

### 4.1 第一版必须聚焦的主能力

第一版只围绕一条主链路展开：

`查单词 -> 看拆解 -> 播放对应讲解片段`

围绕这条主链路，补齐 5 个必要能力：

1. 搜索单词
2. 单词详情解释
3. 视频片段定位播放
4. 云端记录最近查看/收藏/学习状态
5. 用户反馈与缺词登记

### 4.2 第一版必须有的基础设施

这次修订后，我认为下面 4 件事不能再算“以后再说”：

1. `必须有轻量管理后台`
   - 内容录入
   - 单词资料管理
   - 视频打点
   - 缺词反馈处理

2. `必须有云端用户身份`
   - 但不一定一开始就做复杂注册登录
   - 第一版优先使用 `openid` 作为静默身份标识
   - 后续再补手机号登录或显式账号体系

3. `必须有云端学习数据`
   - 最近查看
   - 收藏
   - 学习状态
   - 搜索历史

4. `必须有统一的数据导入与编码规范`
   - 否则乱码问题会反复出现

### 4.3 第一版暂时不做

这些能力可以保留，但不进入首发 MVP：

1. 关系网络星云的完整交互版
2. 系统化背单词模块
3. 复杂课堂商城
4. 强制注册登录流程
5. 积分体系、成就体系、排行榜
6. 复杂裂变玩法

### 4.4 第一版成功标准

如果下面 6 条成立，就说明第一版方向是对的：

1. 用户能在 30 秒内找到一个词并看到讲解。
2. 用户明显感受到“小程序比单看书更容易理解”。
3. 用户愿意连续查多个词，而不是只打开一次。
4. 视频跳转到片段后，用户不会迷失，不会搞不清“现在讲的是哪个词”。
5. 你能收集到真实的高频搜索词和高频缺失词。
6. 你能稳定维护首批 100 到 200 个核心词，而不是被 1000 个词的维护量压垮。

## 5. 建议的一期产品结构

### 5.1 当前原型的结构

你现在的原型已经有 4 个一级入口：

1. 查词
2. 关系网
3. 单词库
4. 课堂

这个结构适合展示方向，但不适合第一版上线验证。

### 5.2 建议的一期正式结构

建议一期小程序收缩成 `2 个一级入口 + 4 个核心二级页面 + 1 个管理后台`。

#### 用户端一级入口

1. `查词`
2. `我的`

#### 用户端二级页面

1. 搜索结果页
2. 单词详情页
3. 视频讲解页
4. 历史/收藏页

#### 辅助页面

1. 缺词登记页
2. 反馈页

#### 内部管理端

1. 内容管理页
2. 视频打点页
3. 缺词处理页
4. 数据导入页

### 5.3 页面流转关系

```text
查词首页
  -> 搜索结果
  -> 单词详情
  -> 视频讲解
  -> 相关词根/词缀详情

查词首页
  -> 最近查看
  -> 单词详情

我的
  -> 历史记录
  -> 收藏
  -> 反馈问卷
  -> 缺词登记

管理后台
  -> 单词内容管理
  -> 视频打点
  -> 缺词处理
  -> 数据导入
```

### 5.4 为什么不建议首发保留 4 个 tab

因为首发版本最怕的是“入口很多，核心价值不清楚”。

如果首页一上来就是查词、关系网、单词库、课堂并列，用户会觉得功能很多，但不知道先用哪一个。

而你的真正核心价值是：

`我遇到一个词看不懂，你马上给我解释。`

所以第一版应该把所有流量先收束到查词。

## 6. 核心页面定义

## 6.1 查词首页

### 页面目标

让用户最快开始一次查词行为。

### 必备模块

1. 搜索框
2. 热门搜索词
3. 最近查看
4. 今日推荐词
5. 一个轻量的课程/服务预告入口

### 页面原则

1. 首页不要承载太多教育内容，重点是促成搜索。
2. 课程入口可以保留，但不要压过搜索入口。
3. 热门搜索和最近查看，本质上都是为了降低输入成本。

---

## 6.2 搜索结果页

### 页面目标

让用户确认自己找到了正确的词。

### 必备模块

1. 精确匹配结果
2. 相近词建议
3. 未收录时的提示
4. 缺词反馈按钮

### 第一版搜索规则建议

第一版先只支持：

1. 从 `完整单词` 搜索进入
2. 再从单词详情页逐层上钻到词根、词缀、字母

不建议第一版一开始就支持复杂的“任意词根反查全库”。

---

## 6.3 单词详情页

### 页面目标

把一个单词讲清楚。

### 必备模块

1. 单词本身
2. 音标
3. 中文释义
4. 象形拆解
5. 词根/词缀说明
6. 书本页码/索引位置
7. 视频讲解入口
8. 相关词或同根词推荐

### 详情页最重要的体验原则

1. 先解释“这个词是什么意思”
2. 再解释“这个词为什么是这个意思”
3. 最后再引导“你还可以继续看哪些相关词”

### 关于“同一个词根有多重意思”

建议这样处理：

1. 每个词根卡片必须显示中文意思，不要只显示字母形式。
2. 如果一个词根有多个常见义项，第一版先显示“主义项 + 补充义项”。
3. 单词详情页里引用词根时，要明确显示当前单词使用的是哪个义项。

---

## 6.4 视频讲解页

### 页面目标

让用户不是“打开一个视频”，而是“直接进入这个词的讲解片段”。

### 这页的核心体验要求

这次修订后，我认为下面 4 个细节是必须做的：

1. `视觉锚点`
   - 播放器下方醒目显示：`正在讲解：study`
   - 同时高亮当前词在片段列表中的位置

2. `重放本词`
   - 提供一个明确的“重放本词”按钮
   - 点击后直接跳回当前词片段的 `start_sec`

3. `清晰的分段导航`
   - 同一视频中的相关词做成横向滚动列表
   - 用户点击某个词，直接跳到对应时间点
   - 这个交互比纯“前一个/后一个”更直观

4. `片段结束后默认停住`
   - 默认播放到当前词片段 `end_sec` 后停住
   - 不要自动无提示地继续播下一个词
   - 下一个词应该由用户主动点

### 页面至少包含

1. 视频播放器
2. 当前命中的单词名
3. 当前词的开始时间和结束时间
4. 重放本词按钮
5. 同视频其他词列表
6. 本词的简短讲解标题

### 第一版不建议做的复杂能力

1. 弹幕
2. 倍速学习统计
3. 复杂章节树
4. 多来源视频聚合

---

## 6.5 我的页面

### 页面目标

给用户一个简单的“复看和同步状态入口”，不是做复杂会员中心。

### 建议保留模块

1. 最近查看
2. 收藏单词
3. 我的反馈
4. 试用问卷
5. 数据同步状态说明

### 账号体系建议

这次修订后的建议是：

1. 第一版 `必须有云端身份`
2. 第一版 `不强制做复杂注册登录`
3. 优先使用 `openid` 静默标识用户
4. 最近查看、收藏、掌握状态都存云端
5. 等验证价值后，再加手机号登录、会员体系、跨设备更精细同步

---

## 7. 内容结构设计

这个产品本质上是内容服务产品，所以第一版真正决定效率的，不是 UI，而是内容结构。

建议把内容拆成下面 8 类对象。

### 7.1 单词对象 Word

建议字段：

- `id`
- `word`
- `phonetic`
- `chinese_meaning`
- `english_meaning`
- `book_page`
- `card_type`
- `levels`
- `pictograph_summary`
- `video_segment_id`
- `related_word_ids`
- `part_ids`

### 7.2 词根/词缀/字母对象 PartCard

建议字段：

- `id`
- `type`
- `symbol`
- `primary_meaning_zh`
- `secondary_meanings_zh`
- `description`
- `parent_ids`
- `related_word_ids`

### 7.3 视频对象 Video

建议字段：

- `id`
- `title`
- `cover_url`
- `video_url`
- `duration_sec`
- `series_name`

### 7.4 视频片段对象 VideoSegment

这个对象非常关键，它直接支撑“按单词跳转到视频时间点”。

建议字段：

- `id`
- `video_id`
- `word_id`
- `start_sec`
- `end_sec`
- `segment_title`
- `next_segment_id`
- `prev_segment_id`

### 7.5 图文正文对象 RichTextBlock

这一点是这次修订里变化最大的地方。

原本我设计过更细的 `ContentBlock` 类型，比如：

- `text`
- `image`
- `image_pair`
- `tip`
- `quote`

这个结构长期更规范，但对你现在这个 MVP 来说，会显著增加前端渲染复杂度，也会增加内容录入成本。

所以更务实的做法是：

`第一版把图文正文统一简化成一个 rich_text_html 字段。`

建议字段：

- `id`
- `word_id`
- `rich_text_html`
- `summary_text`

这意味着：

1. 解释型正文先交给富文本编辑器维护
2. 前端只渲染一套富文本容器
3. 图片一张、两张并排、提示框这些排版，优先在内容端完成
4. 以后有资源，再把稳定的版式抽成原生结构化组件

### 7.6 缺词反馈对象 MissingWordFeedback

这块不能只做一个随便可输的文本框，否则后续会变成垃圾箱。

建议字段：

- `id`
- `openid`
- `missing_word`
- `book_page_hint`
- `feedback_type`
- `status`
- `created_at`

### 7.7 用户学习状态对象 UserWordState

建议字段：

- `id`
- `openid`
- `word_id`
- `is_favorited`
- `is_mastered`
- `last_viewed_at`
- `view_count`

### 7.8 内容导入任务对象 ImportJob

为了从源头解决乱码和数据混乱，建议把导入过程本身也当成一类正式对象。

建议字段：

- `id`
- `source_type`
- `source_filename`
- `source_encoding`
- `target_schema`
- `import_status`
- `created_at`

## 8. 建议的技术架构

为了让这个项目更适合继续 vibe coding，建议把架构理解成 5 层。

## 8.1 前端层

前端层只负责：

1. 展示页面
2. 处理点击和跳转
3. 渲染富文本
4. 播放视频
5. 展示云端同步结果

前端层不要继续把大量业务数据直接写死在页面组件里。

## 8.2 内容层

内容层是这个项目最核心的一层。

它负责：

1. 单词资料
2. 拆解资料
3. 视频与时间点映射
4. 书本页码索引
5. 富文本讲解正文

## 8.3 用户服务层

用户服务层第一版至少要提供：

1. 搜索单词
2. 获取单词详情
3. 获取视频片段
4. 记录最近查看
5. 记录收藏
6. 记录学习状态
7. 提交反馈和缺词登记

## 8.4 管理后台层

这次修订后，我认为后台不再是“后面再做”，而是 MVP 必备。

第一版后台不需要很漂亮，但必须能做下面 4 件事：

1. 录入和编辑单词资料
2. 管理视频与片段映射
3. 查看和处理缺词反馈
4. 导入和校验内容数据

## 8.5 数据治理层

这一层的作用是避免后面长期救火。

必须先定：

1. 所有原始文本统一 UTF-8
2. Excel 导出统一使用 `CSV UTF-8`
3. 数据库字符集统一 `utf8mb4`
4. 导入脚本必须记录编码来源
5. 每次导入前做乱码检测

## 9. 第一版最该先补的 8 个接口与内部工具边界

### 9.1 搜索接口

作用：

输入单词，返回匹配结果和是否收录。

### 9.2 单词详情接口

作用：

返回单词释义、拆解、词根说明、书页索引、相关推荐、富文本讲解。

### 9.3 视频片段接口

作用：

返回这个词对应的视频、开始时间、结束时间、片段标题、同视频中的相邻词列表。

### 9.4 用户身份与同步接口

作用：

基于 `openid` 建立静默身份，并同步：

- 最近查看
- 收藏
- 学习状态

### 9.5 用户反馈与缺词登记接口

作用：

提交“看不懂、搜不到、书里有但视频没讲”等反馈。

同时要做输入限制：

1. 只允许英文单词
2. 限制长度
3. 支持附带页码提示

### 9.6 内容管理后台接口

作用：

让内部人员能录入和修改：

- 单词内容
- 富文本讲解
- 视频信息
- 页码索引

### 9.7 视频打点工具

作用：

让内容人员在后台边看视频边标记：

- `start_sec`
- `end_sec`
- `word_id`
- `segment_title`

这不是锦上添花，而是降低录入成本的关键工具。

### 9.8 数据导入与编码校验工具

作用：

在导入 Word、Excel、CSV、文本资料时，统一：

- 编码
- 字段映射
- 乱码检测
- 错误日志

## 10. 当前原型到正式 MVP 的重构建议

### 10.1 保留并继续打磨

1. 搜索首页
2. 单词详情页
3. 单词拆解卡片
4. 视频讲解入口

### 10.2 升级处理

这部分不能再按原计划“先本地凑合”：

1. 最近查看、收藏、学习状态改为 `openid + 云端存储`
2. 内容管理改为后台维护，不继续写死在前端页面里
3. 单词讲解正文改为富文本输入，不做多套前端块渲染

### 10.3 延后处理

1. 关系网页完整交互版
2. 背单词模块
3. 复杂统计页
4. 完整课程商城

### 10.4 必须尽快处理的基础问题

1. 统一内容数据结构
2. 建立 UTF-8 导入规范
3. 清理现有乱码数据
4. 把页面内硬编码的数据抽出来
5. 定义视频与单词的时间点映射
6. 搭建轻量管理后台
7. 开发视频打点工具
8. 设计缺词反馈的审核闭环

## 11. 团队分工建议

假设是一个 2 到 3 人的小团队，建议这样分工。

### 11.1 UI / 前端

负责：

1. 首页搜索体验
2. 单词详情页布局
3. 视频页体验
4. 历史/收藏/反馈页
5. 小程序适配和交互收敛

重点不是把页面做得很花，而是让用户几步之内看懂、查懂、回放懂。

### 11.2 开发 / 架构

负责：

1. 内容数据结构定义
2. 搜索、详情、视频片段接口设计
3. `openid` 身份与云端学习状态
4. 管理后台
5. 视频打点工具
6. 数据导入与编码治理

### 11.3 测试 / 试用运营

负责：

1. 核心路径验收

### 12.1 功能验收

## 15. 本轮评审后的最终结论

这次修订后，产品方向更务实了。

我同意的核心变化有：

1. 管理后台不是可选项，而是 MVP 必备。
2. 云端身份和云端学习数据不是以后再说，而是一开始就该有。
3. 视频跳点不能只做“能跳过去”，必须把“不会迷失”一起设计进去。
4. 缺词反馈必须做输入约束和后台闭环。
5. 视频打点工具很值得优先做。
6. 乱码问题必须从数据源和导入链路解决。

我唯一不完全同意的是：

`第一版必须做完整注册登录。`

更务实的版本应该是：

`第一版必须有云端身份和云端同步，但优先用 openid 静默身份，不强制用户先注册。`

这样既能保证数据不丢，又不会把 MVP 的登录链路做重。

最终第一版最重要的，不是功能数量，而是把下面这件事做透：

`用户搜到一个词后，能立刻明白这个词，并且听到真正有帮助的解释。`
