# 内容权限与商业规则设计方案

版本：v1.1
日期：2026-08-28
适用范围：微信小程序、Node server、管理后台、用户权益系统、视频播放链路。

本文档定义《象形英语》小程序第一阶段商业闭环中的内容访问规则、权益消费规则、会员规则和 API 权限边界。后续涉及内容权限、权益扣减、视频访问、买书会员、分享奖励的开发，应以本文档为准。

## 1. 核心原则

1. 用户必须登录后才能查看完整学习内容。
2. 注册用户获得 30 次完整学习次数。
3. 每进入一个单词完整详情，消耗 1 次完整学习次数。
4. 会员期间可无限查看完整内容，不消耗次数。
5. 买书用户可通过后台赠送或现有购书福利码兑换获得 30 天全站会员。
6. 普通无权益用户只能查看基础免费内容。
7. 权限判断必须在 server 完成，前端隐藏只能作为体验层处理，不能作为权限控制。
8. 付费内容字段不得通过公开接口、搜索接口、基础详情接口返回。

## C. 次数消费规则

### C1. 消费单位

一次完整学习次数对应一次完整单词详情访问。

完整单词详情访问指用户主动请求并获得以下完整学习内容中的任意组合：

- 象形拆解
- 完整改义
- 完整意象
- 视频片段
- 完整讲解视频
- 深度学习内容

### C2. 会消耗次数的场景

以下行为应视为主动进入完整学习内容，若用户不是有效会员，应消耗 1 次：

1. 从搜索结果进入单词完整详情。
2. 从首页推荐进入单词完整详情。
3. 从收藏列表进入单词完整详情。
4. 从最近学习列表重新进入单词完整详情。
5. 从关联词、词根、扩展内容跳转到另一个单词的完整详情。

第一阶段暂不支持“已学过免扣”“复习模式免扣”“同一单词永久解锁”。因此，用户重复进入同一个单词完整详情，仍按一次新的完整学习访问处理。

### C3. 不消耗次数的场景

以下行为不得消耗次数：

1. 首页浏览。
2. 搜索单词。
3. 搜索结果列表展示。
4. 首页推荐列表展示。
5. 收藏列表展示。
6. 最近学习列表展示。
7. 基础免费详情展示。
8. 权益状态查询。
9. 登录、注册、用户资料刷新。

### C4. 扣减成功条件

一次次数消费必须同时满足：

1. 用户已登录且身份有效。
2. 用户不是有效会员。
3. 用户剩余完整学习次数大于 0。
4. 用户主动请求完整学习内容。
5. server 成功完成权益校验和扣减。
6. server 返回完整内容或可恢复的访问结果。

如果用户是有效会员，应允许访问完整内容，但不扣次数。

### C5. 幂等与失败处理

完整内容访问请求必须携带客户端生成的 `clientRequestId` 或等价幂等标识。

同一个 `clientRequestId` 的重试请求不得重复扣减。若出现网络超时、客户端中断或视频加载失败，应允许用户在同一访问上下文中重试，不应额外消耗次数。

如果 server 已扣减但客户端未收到完整内容，应通过幂等查询或重试机制恢复本次访问结果，避免用户感知为“扣了次数但没看到内容”。

## D. 会员规则

### D1. 会员定义

会员为全站会员。会员有效期内，用户可以无限查看所有已发布单词的完整学习内容。

会员权益包括：

- 象形拆解
- 完整改义
- 完整意象
- 视频片段
- 完整讲解视频
- 深度学习内容

### D2. 会员访问规则

1. 会员访问完整内容不消耗完整学习次数。
2. 会员访问完整内容仍应记录学习行为，便于最近学习、数据分析和风控。
3. 会员访问完整内容仍应通过 server 权限校验。
4. 会员状态不得只由前端本地缓存判断。

### D3. 会员过期规则

会员过期后，用户恢复普通用户状态：

1. 若仍有剩余完整学习次数，可继续按次访问完整内容。
2. 若无剩余完整学习次数，只能查看基础免费内容。
3. 过期用户不得继续访问象形拆解、意象、视频、深度学习内容。

### D4. 会员与次数并存规则

会员期间不消耗次数。用户已有的剩余次数保留，会员过期后继续可用，除非未来另行定义次数有效期。

## E. 买书会员规则

### E1. 后台人工添加

后台赠送固定 30 天会员的能力已经实现，可用于经过人工核验的运营赠送。

默认规则：

- 权益类型：全站会员
- 默认有效期：30 天
- 生效方式：管理员在后台人工添加
- 消耗规则：会员期间无限访问完整内容，不消耗次数
- 到期规则：到期后恢复普通用户状态

后台操作应记录：

1. 用户标识。
2. 会员开始时间。
3. 会员到期时间。
4. 权益来源：买书用户。
5. 操作管理员。
6. 操作备注。
7. 操作时间。

### E2. 购书福利码兑换

购书福利码兑换已经实现，当前规则为：

1. 后台在客服完成购书核验后签发兑换码。
2. 每个兑换码对应 30 天全站会员。
3. 用户在小程序内输入兑换码。
4. server 校验兑换码有效性。
5. 兑换成功后开通会员。
6. 兑换成功后记录兑换用户，不可重复使用。
7. 后台可按操作号查询签发状态，并支持必要的补发操作。

兑换码至少应包含以下状态：

- 未使用
- 已使用
- 已作废
- 已过期

### E3. 订单自动化

未来若接入电商订单或会员支付，应由经过服务端验证的支付成功或订单确认事件自动发放会员。订单自动化当前尚未实现；现有后台赠送和购书福利码兑换不等同于会员购买。

## F. 分享奖励规则

### F1. 当前状态

分享拉新的第一版产品规则已经锁定，但页面、邀请关系、接口、服务端资格判断和奖励触发当前均尚未实现。实施前不得把规则描述成已上线能力。

### F2. 已锁定的第一版规则

第一版分享拉新规则如下：

1. 新用户继续复用现有 `REGISTER_BONUS` 获得 30 次完整学习次数，不另建新人额度逻辑。
2. 邀请者在有效新人完成手机号注册后额外获得 30 次，写入 `SHARE_REWARD +30` 权益流水。
3. 分享、点击邀请链接或仅打开小程序都不发奖励。
4. 有效新人必须从有效邀请链接进入，在邀请落地页完成手机号快捷登录，并在手机号身份解析后最终创建新的 `users` 记录。
5. 新人资格以手机号对应的最终账号为准。手机号已属于现有账号时，即使当前微信身份第一次出现，也不算新人；微信身份合并到已有手机号账号时不奖励。
6. 注册前采用最后一次有效邀请。手机号注册成功后永久锁定邀请关系，注册成功后不允许补录、更换或覆盖。
7. 邀请 token 有效期为 7 天。token 过期后用户仍可正常注册并获得普通注册权益，但邀请者不获得奖励。
8. 新人注册 30 次和邀请者奖励 30 次的有效期均为一年。
9. 每位邀请者累计最多获得 5 次奖励，即最多额外获得 150 次。
10. 同一个新人只能触发一次有效邀请奖励。
11. 禁止自邀。识别为自邀时提示“该邀请无效，不能邀请自己”，但不得影响正常登录及普通注册权益。
12. 第一版不做复杂站内消息；邀请者进入“我的”页面后刷新权益余额即可。
13. 邀请资格、关系锁定、累计上限和奖励发放必须由 server 判断，并具备并发与重试幂等保护。

### F3. 防刷原则

分享奖励上线前必须具备基础防刷规则：

1. 邀请关系应以唯一新人用户为约束，避免同一个新人并发绑定多个邀请者。
2. 注册奖励继续使用现有 `registration_bonus:{user_id}` 幂等保护；邀请奖励使用独立且可追溯的邀请记录生成幂等键。
3. 邀请者和新人不得是同一个最终用户账号。
4. 不仅凭同设备直接拒绝正常家庭成员注册；设备、手机号、微信身份等异常组合可进入风险记录或人工复核。
5. 后台至少可通过权益流水查询 `SHARE_REWARD` 的来源和结果；邀请关系明细由后续邀请记录查询能力承载。

### F4. 获取学习权益入口

采用统一“获取学习权益页”方案，当前尚未实施：

1. 详情页额度不足时继续保留一个主按钮：“开通会员或获取更多次数”。
2. 点击后进入新增的“获取学习权益”页。
3. “我的”页增加“获取学习权益”常驻入口。
4. 权益获取页展示“购买 30 天会员”和“邀请好友得 30 次”。
5. 页面提供轻量“活动规则”入口，进入邀请规则页。
6. 需要强调主次时，会员购买更突出，邀请奖励次之。

## G. API 权限设计原则

### G1. 返回对象分层

API 应明确区分基础内容和完整内容。

`basicWord` 用于公开或半公开场景：

- 搜索结果
- 首页推荐
- 基础详情
- 收藏列表
- 最近学习列表
- 无权益锁定态页面

`basicWord` 可以包含：

- id
- word
- phonetic
- basicMeaning
- coverImage
- 基础词卡展示所需字段
- access 状态摘要

`basicWord` 不得包含：

- 象形拆解详细内容
- 完整改义
- 完整意象
- 视频 URL
- 视频 fileId
- 完整视频播放地址
- 深度学习内容

`fullWord` 仅用于完整权限通过后的场景：

- 已登录且有剩余次数
- 有效会员
- 后台管理员预览

`fullWord` 可以包含：

- basicWord 的全部字段
- 象形拆解
- 完整改义
- 完整意象
- 视频片段
- 完整讲解视频
- 深度学习内容
- 权益消费结果

### G2. 推荐接口原则

建议完整内容访问使用会产生明确副作用的接口，例如：

```text
POST /api/words/:id/access
```

该接口负责：

1. 校验登录态。
2. 判断会员状态。
3. 判断剩余次数。
4. 执行扣减或会员免扣。
5. 返回完整内容。
6. 返回本次访问结果。

搜索、首页、基础详情等接口不得触发扣减。

### G3. 权限结果字段

完整内容接口建议返回明确的访问状态：

```json
{
  "access": {
    "level": "full",
    "canAccessFull": true,
    "charged": true,
    "chargeAmount": 1,
    "remainingQuota": 29,
    "membershipActive": false,
    "reason": null
  }
}
```

无权限时应返回基础内容和锁定原因，而不是只返回通用错误：

```json
{
  "basicWord": {},
  "access": {
    "level": "basic",
    "canAccessFull": false,
    "charged": false,
    "remainingQuota": 0,
    "membershipActive": false,
    "reason": "QUOTA_INSUFFICIENT"
  }
}
```

### G4. 视频权限原则

视频属于付费内容。任何公开接口、搜索接口、基础详情接口不得返回视频播放地址。

视频字段只能在完整内容权限通过后返回。后续接入腾讯云 VOD 播放签名时，应优先返回短时有效播放凭证，而不是长期可复制 URL。

### G5. 前端职责

前端负责：

1. 根据 API 返回结果展示基础内容、完整内容或锁定态。
2. 在用户进入完整内容前提示登录或权益消耗。
3. 展示剩余次数、会员状态、到期时间。
4. 处理网络失败、视频失败、权益不足等体验状态。

前端不得作为唯一权限边界。

## H. 后续开发注意事项

1. 先完成 server 侧 `basicWord` / `fullWord` 权限分层，再优化前端展示。
2. 未登录用户请求完整内容时，server 不得返回付费字段。
3. 已登录但无次数、非会员用户请求完整内容时，应返回基础内容和锁定原因。
4. 会员用户访问完整内容时，应记录学习行为，但不得扣减次数。
5. 后台赠送和购书福利码兑换流程需要保留操作、兑换与会员 grant 记录，便于追踪和售后。
6. 分享奖励和会员购买尚未实现，只有在对应服务端资格判断、订单或邀请闭环完成后才能开放入口。
7. 视频 URL、视频 fileId、播放凭证都视为付费字段。
8. 所有扣减行为必须有权益流水记录。
9. 所有完整内容访问应具备幂等标识，避免重复扣减。
10. 文案中应统一使用“完整学习次数”，避免使用“查词次数”造成误解。
11. 收藏、最近学习只是入口，不代表用户永久拥有该单词完整内容。
12. 后续若增加“已学过免扣”“复习模式”“永久解锁”，必须先更新本文档，再进行开发。

## I. 第一阶段推荐开发顺序

1. 明确并实现 `basicWord` / `fullWord` 返回结构。
2. 修正搜索、首页、基础详情接口，确保只返回免费字段。
3. 建立完整内容访问接口，统一处理登录、会员、次数扣减。
4. 加入幂等访问标识，防止网络重试重复扣减。
5. 调整详情页为基础内容 + 完整学习区 + 锁定态结构。
6. 将视频字段限制在完整权限通过后返回。
7. 优化我的页面，展示剩余完整学习次数、会员状态和到期时间。
8. 后台赠送 30 天会员和购书福利码兑换已经完成，后续不得与付费订单混为同一来源。
9. 分享奖励和订单自动化进入后续阶段；后台赠送 30 天会员和购书福利码兑换已经实现。

## J. 30 天会员购买、退款与支付渠道边界

本节记录 2026-08-28 已锁定的第一版产品规则。订单、支付、购买页面和退款联动当前均尚未实现。

### J1. 会员商品与购买确认

1. 商品价格暂定 30 元。
2. 购买形式为单次购买 30 天，不做自动连续包月。
3. 30 天定义为固定 `30 × 24` 小时。
4. 允许多次购买，并按照现有会员排期顺序叠加，不缩短已有有效期。
5. 当前购买会员权益仅包括：有效期内查看完整学习内容不扣完整学习次数。
6. 购买入口位于统一“获取学习权益”页，并进入独立购买确认页面。
7. 支付前提供会员服务说明和退款规则入口；会员购买、有效期、价格和退款条件必须清晰可访问，不应隐藏为用户难以发现的说明。
8. 商品价格、权益时长和订单金额由 server 确定，不能信任客户端传值。

### J2. 支付确认、发放与后台边界

1. 小程序端支付成功回调只用于界面提示、触发查单或刷新展示；支付成功必须以支付平台服务端通知或服务端主动查单的验证结果为准，不能根据客户端回调直接发放会员。
2. 支付成功后复用现有会员 grant、排期、权益流水和快照能力。
3. 同一支付订单的通知处理、主动查单和补单必须进入同一个幂等会员发放入口，并记录支付订单与会员 grant 的稳定关联。
4. 支付闭环必须覆盖重复通知、通知丢失、主动查单补偿和发货确认；只有会员发放事务成功后才能确认发货完成。
5. 后台不允许人工把订单直接修改为支付成功。
6. 补单只能重新查询支付平台，在确认真实支付成功后幂等补发会员。
7. 超时未支付订单由 server 自动关闭。
8. 后台第一版提供订单查询、支付状态同步和权益发放结果查询。

### J3. 非 Apple IAP 退款规则

本节适用于由商户自行控制退款决定的非 Apple IAP 支付渠道：

1. 尚未生效的叠加会员订单可以全额退款，并撤销该订单对应的未来 30 天。
2. 已经生效 24 小时内且没有使用过会员权益，可以全额退款，并撤销该订单对应的会员权益。
3. 已经使用过会员权益，不允许退款，会员时间不撤销。
4. “使用过会员权益”指该订单对应的会员时间已经生效后，用户至少成功访问过一次原本需要扣减次数的完整学习内容。
5. 退款资格判断必须依据可靠的服务端会员使用事实，不能依据客户端上报。当前会员免扣访问尚未记录这种事实，因此完整退款闭环在现网开放前仍有阻断；具体采用现有权益流水还是独立使用事实记录，需在代码开发前另行审查。
6. 第一版退款可以先在支付商户平台操作，但系统必须接收或主动同步退款结果。
7. 订单退款、支付退款状态和对应会员 grant 的撤销结果必须可追溯。
8. 退款与会员撤销必须具备幂等保护，重复通知不能重复撤销。

### J4. Apple IAP 退款规则

1. iOS Apple IAP 订单的退款申请和最终结果以 Apple 平台规则为准。
2. 系统必须接收或同步平台退款结果。
3. Apple 已退款时，撤销该订单尚未使用的剩余会员权益；已经过去或已经消耗的历史时间无法追回。
4. 会员协议应明确：“iOS 端通过 Apple App 内购买产生的订单，其退款申请和处理结果适用 Apple 平台规则；其他支付渠道适用本服务退款规则。”

### J5. 支付渠道边界

1. 30 天会员属于解锁数字学习内容的虚拟权益，第一版采用微信小程序虚拟支付的“道具直购/主动支付”，调用 `wx.requestVirtualPayment` 并使用 `mode=short_series_goods`。
2. 第一版不使用普通微信 JSAPI `wx.requestPayment`，不使用代币充值，也不使用 Android/鸿蒙或 Apple 的自动续费会员订阅能力。
3. Android、鸿蒙、Windows 先使用普通虚拟支付沙箱完成基础联调。
4. iOS 一次性购买仍采用虚拟支付道具直购，由官方接口按设备进入 Apple 支付；Apple 支付不支持沙箱，必须留到受控现网真实交易阶段。普通端沙箱通过不代表 iOS 已验收。
5. “获取学习权益”页保持统一，但订单和支付设计必须按平台、渠道和环境隔离，不得锁死为普通 `wechat_pay`。
6. 个人收款码、站外付款引导、将虚拟权益按实体商品申报、审核后远程改变支付入口等方式存在平台审核、支付权限、消费者纠纷和账号处罚风险，不属于已锁定或已批准的第一阶段方案。
7. 上述替代路径保留为风险备选，只有在核实平台和支付规则并取得产品负责人明确确认后才能重新评估；开发不得自行实现、隐藏或远程开启。

订单模型至少为不同渠道预留以下信息：

- `payment_channel`
- `platform`
- `provider_order_id`
- `provider_transaction_id`
- `paid_amount`
- `currency`
- `refund_status`

2. 支付及退款消息推送配置和可达性。
