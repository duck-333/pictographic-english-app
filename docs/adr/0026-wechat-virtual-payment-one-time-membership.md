# ADR-0026: 微信虚拟支付一次性 30 天会员接入决策

日期：2026-08-28

状态：Proposed

## 背景

项目已具备注册额度、完整内容访问扣次、会员免扣、固定 30 天会员 grant、顺序排期、权益流水、当前快照、后台赠送会员和购书福利码兑换能力，但尚未实现会员购买、支付订单、退款及虚拟支付协议接入。

第一版需要销售一次性 30 天学习会员。本 ADR 记录稳定的商品、渠道、支付确认、安全和实施边界；具体接口参数、错误码和后台操作步骤以开发时的微信官方文档为准。

## 已锁定的商品规则

- 价格暂定 30 元，由 server 确定并校验。
- 单次购买固定 `30 × 24` 小时，不是自然月。
- 不自动续费。
- 允许重复购买，并按现有会员 grant 排期顺序顺延。
- 会员有效期间查看完整学习内容不扣普通次数。

## 支付产品选择

### 采用道具直购

一次性 30 天会员采用微信小程序虚拟支付的“道具直购/主动支付”。小程序调用 `wx.requestVirtualPayment`，支付模式使用：

```text
mode=short_series_goods
```

该模式与“一次支付获得一段固定期限的数字学习权益”一致，支付成功后由项目现有会员 grant 能力发放固定时长。

### 不采用代币

第一版不存在充值代币、代币余额或二次消费场景。引入代币会增加余额、充值、扣减和退款链路，不能为单个会员商品提供必要价值，因此不使用代币充值模式。

### 不采用自动续费会员订阅

第一版明确不连续包月，不建立周期扣费关系，因此不使用 Android/鸿蒙会员订阅、支付中签约或 Apple 自动续费会员订阅。也不使用普通微信 JSAPI `wx.requestPayment`。

## 平台、渠道与环境边界

- Android、鸿蒙、Windows：先使用普通虚拟支付沙箱完成创建业务订单、签名、拉起支付、通知、查单、发货和会员发放联调。
- iOS：一次性购买仍采用虚拟支付道具直购，由 `wx.requestVirtualPayment` 按设备进入 Apple 支付。
- iOS Apple 支付不支持沙箱，只能留到受控现网真实交易阶段。
- 普通端沙箱验证通过不代表 iOS 支付已经验收。
- 沙箱与现网必须使用各自的商品发布状态、AppKey 和环境标识，不能混用。
- 费率属于时效性平台政策，不进入永久商品或权益规则。

## 支付确认与会员发放

客户端支付成功回调只用于界面提示、触发服务端查单或刷新订单状态，不能直接发放会员。

真实支付状态必须由以下任一服务端事实确认：

1. 支付平台服务端通知；
2. 服务端主动查单结果。

通知、主动查单和补单必须进入同一幂等会员发放入口。确认支付成功后，订单/支付服务使用稳定业务订单 ID 调用现有会员 grant 事务，创建会员 grant、权益流水并更新当前快照，同时记录支付订单与 grant 的关联。

支付闭环必须覆盖：

- 重复通知；
- 通知丢失；
- 主动查单补偿；
- 会员发放失败后的安全重试；
- 发货确认；
- 本地订单、平台订单和权益发放状态不一致时的人工查询。

只有本地会员发放事务成功后才能确认发货完成。后台不得人工把订单直接修改为支付成功；补单必须先重新查询支付平台。

## 订单、退款与权益事实边界

订单/支付域负责业务订单、运行环境、渠道、客户端平台、平台订单标识、金额以及支付、发货和退款状态。权益域继续负责会员 grant、权益流水和当前快照。

本轮只锁定两者必须通过稳定订单 ID 建立可审计关联，不锁定最终表名、全部字段或 migration 结构。

同一订单只能发放一次会员。支付确认、订单状态、会员 grant、权益流水和快照更新需要明确事务边界；外部通知回复发生在本地事务成功之后。退款事实、平台退款状态和会员 grant 撤销也必须分别可追溯并具备幂等保护。

## 支付初始化签名链路缺口

虚拟支付需要 AppKey 支付签名和基于本次 `session_key` 的用户态签名。当前项目 `code2Session()` 没有向支付初始化链路提供签名所需的 `session_key`，因此现状不能完成支付初始化。

后续方向是由小程序取得新的 `wx.login` code，服务端临时换取并使用 `session_key` 生成用户态签名。`session_key` 不得返回客户端，也不得长期明文保存。具体身份核对、生命周期和错误恢复方案必须在代码开发前单独审查。

该缺口阻断普通端虚拟支付沙箱联调。

## 会员使用事实与退款缺口

已锁定的非 Apple IAP 退款规则要求判断对应会员时间是否已经用于完整内容访问。当前会员免扣访问没有记录可靠的服务端会员使用事实，因此无法执行“生效 24 小时内且未使用可退款”的完整判断。

这一缺口不阻断普通端支付沙箱、主动查单和会员发放的基础联调，但在开放正式退款或现网购买前必须解决。后续需要比较：

1. 复用现有权益流水记录会员使用事实；
2. 新增独立的会员使用事实记录。

本 ADR 不预先选择其中一种方案。无论采用何种实现，退款资格不得依赖客户端上报，并必须能关联实际生效的会员 grant。

## AppKey 与鉴权安全边界

- AppKey 只存在于受控服务端密钥环境，不进入仓库、客户端、日志、权益流水或文档。
- 沙箱与现网 AppKey 必须隔离，并与请求环境严格匹配。
- `session_key` 只在服务端支付初始化链路中短暂使用。
- 参与签名的支付参数字符串必须与实际请求保持一致。
- 当前虚拟支付核心鉴权涉及小程序 `access_token`、虚拟支付 AppKey、`session_key` 用户态签名和相关消息推送。
- 普通微信支付商户 API v3 不是本方案默认的核心支付前置项；未来接入其他渠道时再单独确认 API v3 密钥、商户私钥和证书要求。

## 当前后台确认状态

产品负责人于 2026-08-28 通过微信后台确认：

- 虚拟支付入口已开通；
- AppID 与商户号已绑定；
- OfferID 已生成；
- 沙箱和现网 AppKey 已生成；
- 苹果 IAP 支付显示已开通；
- Android/鸿蒙/Windows 当前费率显示为 1%；
- iOS 当前费率显示为 12%。

本轮代码审查没有登录微信后台独立验证以上状态，且未读取任何 AppKey 或 OfferID 值。

## 仍需人工确认

- 30 天会员商品名称、标识、图片和说明；
- 商品在沙箱与现网的配置、审核、发布和生效状态；
- 支付、退款消息推送配置及可达性；
- 小程序简称；
- 当前服务类目和数字学习会员销售资格；
- iOS Apple 支付现网可用性；
- 受控现网真实交易与退款验收安排；
- 费率优惠、投诉处理及其他运营合规要求。

## 第一阶段范围

- 单个一次性 30 天会员商品；
- Android、鸿蒙、Windows 普通虚拟支付沙箱；
- 服务端商品定价和支付参数生成；
- AppKey 支付签名和 `session_key` 用户态签名；
- 业务订单、支付状态和会员 grant 关联；
- 支付通知、主动查单、幂等发放、发货确认和补偿；
- 最小订单与权益发放结果查询。

iOS 仅保留兼容设计，实际交易验收进入受控现网阶段。

## 第一阶段明确排除

- 自动连续包月及任何周期代扣；
- Android/鸿蒙自动续费会员订阅；
- Apple 自动续费会员订阅；
- 代币充值和代币消费；
- 普通微信 JSAPI 支付；
- 多商品商城、优惠券、活动价和免费试用；
- 站外付款、个人收款码或远程隐藏支付入口；
- 人工把订单改为支付成功；
- 未经受控验收的 iOS 正式购买；
- 生产部署。

## 后果

正向影响：商品语义、平台渠道、支付确认和现有会员权益模型保持清晰分工；普通端可先在沙箱验证，iOS 风险被隔离到受控现网阶段。

成本：需要新增订单和支付协议能力，补齐支付签名链路、通知与查单补偿，并在现网开放前解决会员使用事实和完整退款闭环。
